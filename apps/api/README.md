# @team27/api

La API HTTP en NestJS 12, en `http://localhost:3001/api`. Compone los contextos hexagonales y los expone; la base le llega por [`@team27/data-main`](../../data/main/README.md).

## Comandos

```sh
pnpm dev:api                          # nest start --watch (o pnpm dev, con la web)
pnpm nx run @team27/api:build         # nest build → dist/
pnpm nx run @team27/api:start         # node dist/main.js
pnpm nx run @team27/api:test          # Vitest
```

## Rutas

Todas cuelgan de `/api`. Los POST responden 201, salvo los que dicen 200 o 204. Los errores traen `{ statusCode?, code, message }`.

Las rutas del proyecto (espacios, lo vigente, propuestas, avisos y eventos) cuelgan de `/projects/:projectId` y piden `Authorization: Bearer <token de Auth0>`. Para leer, el proyecto tiene que ser de una de tus organizaciones (404 `not_found` si no, o si no existe). Para escribir, además tienes que estar en el equipo del proyecto (403 `not_on_team`): quien actúa es tu cuenta, y su id es el de tu lugar en el equipo. Un proyecto creado desde la web tiene como único integrante a quien lo creó.

| Ruta | Responde |
| ---- | -------- |
| `GET /health` | `{"status":"ok"}` si el proceso vive. No toca la base |
| `GET /health/ready` | `{"status":"ok","database":"ok"}`, o 503 `{"status":"unavailable","database":"error"}` si la base no responde |
| `GET /projects/:projectId/spaces` | `{ spaces }`: cada espacio con sus documentos (`state`: `current`, `stale`, `discrepancy` o `acknowledged`), revisiones, sus fragmentos (con el texto y lo rechazado por la inferencia) y hechos con su resultado y su confianza |
| `GET /projects/:projectId/areas` | La ocupación vigente: `levels`, `axes` (longitudinales con sus metros y transversales), `spans`, `cells`, `systems`, `occupants` (huella `areas` de cada elemento con espacio, `proposed` si un PR abierto la mueve, quién la respalda y los solapamientos vivos que toca) y `overlaps` vivos |
| `GET /projects/:projectId/overlaps?status=` | `{ overlaps }`. `status`: `abierto`, `confirmado`, `descartado`, `resuelto` o `activo` (abiertos y confirmados). Cada uno trae `id`, `kind`, `status`, `relation`, `title`, `area` (`nivel`, `celda`, `sistemas`, `label`), los dos elementos, `chunkLocator`, la revisión, `otherBacking`, `proposalId`, `otherProposalId`, `validators`, `votes`, `resolution` y las fechas |
| `POST /projects/:projectId/overlaps/:id/vote` | 200. `{ kind: 'se_tocan' \| 'no_se_tocan', note? }` de un validador (`x-action-id` lo hace idempotente). Responde `{ overlap, proposal, merged, stale, projectVersion }`. 403 `not_validator` si no valida ese solapamiento; 409 `invalid_state` si cambia su voto o el solapamiento ya no admite votos |
| `GET /projects/:projectId/baseline?section=` | `{ version, totals, entries }`: lo vigente con `status` (`confirmed`, `proposed`, `disputed`), `proposedValue`, `sources`, `staleCount` y `version`. `section`: `estructura`, `instalaciones`, `fachada`, `costos` o `plazo` |
| `GET /projects/:projectId/baseline/:subjectId/:attribute/provenance` | La cadena de procedencia: valor vigente y anteriores con revisión, espacio, autor, propuesta, votos con nota y hora y discrepancias que lo respaldaron; 404 si no hay valor |
| `POST /projects/:projectId/revisions` | La puerta genérica de ingesta: `{ documentId, label, spaceId, pointer, contentHash?, chunks: { locator, kind: 'fila' \| 'anotacion' \| 'acuerdo' \| 'mensaje' \| 'parametro' \| 'texto', text?, claims?: { subject, attribute, value, unit, role: 'afirma' \| 'usa', confidence? }[] }[] }`. Un fragmento con `claims` es estructurado; uno con `text` y sin `claims` es de texto libre y lo lee `context/impact` (evidencia: el texto más el título del documento y la revisión; confianza mínima 0,7). El `claims` de primer nivel sigue valiendo como fragmentos implícitos de tipo `fila`, uno por localizador. Solo la sube el dueño del documento (403 `not_your_document`). Ejecuta toda la cadena y responde 201 `{ revisionId, claims, chunks, proposals, overlaps, resolvedOverlaps, discrepancies, backed, stale }`. `claims` trae `confidence` y `locator`; `chunks`, `source` (`estructurado` o `inferencia`) y lo `rejected`. `proposals` trae como mucho una (el PR de la revisión): `id`, `changeId`, `documentId`, `label`, `authorId`, `title`, `status`, `costDelta`, `delayDays`, `reviewers` (ids), `filtered`, `hunks` (`subjectId`, `attribute`, `before`, `after`, `locator`, `changed`), `unchangedHunks`, `blockedByOverlap` y `waitingFor`. Idempotente con `x-action-id`. No exige un orden entre revisiones |
| `GET /projects/:projectId/inbox` | `{ castId, items, authoring }`: tu bandeja en el proyecto. Solapamientos por validar (`type: 'overlap'`, con `myVote`), votos (con progreso y `blockedByOverlap`), discrepancias, desfases y filtrados que te tocan, y las propuestas activas que escribiste |
| `GET /projects/:projectId/events?after&limit` | Sondeo con cursor de los eventos del proyecto: `{ cursor, reset, events }`. Sin `after`, solo el cursor actual; con `after` por delante del servidor, `reset: true` sin eventos; sin novedades, `events: []`. `limit` 1 a 200 (100 por defecto). Cada evento trae `seq`, `kind`, `message`, `refs` y `at` |
| `GET /integrations/projects/:projectId` | Con token, y el proyecto tiene que ser de una de sus organizaciones (404 `not_found`). `{ google: { configured, connection: { accountEmail, connectedAt } \| null, pollSeconds, push: { enabled, reason, fallbackSeconds } }, sources }`: el estado del conector de Google Sheets, con la cuenta de Google de quien mira (`google.push` dice si los avisos de Drive están activos, con `reason` cuando no lo están y `fallbackSeconds` para la revisión de respaldo), y las planillas vinculadas a ese proyecto (`title`, `pointer`, `checkedAt`, `changedAt`, `changedBy` (`{ name, email } \| null`, quien hizo el último cambio), `lastError` y `push: { active, expiresAt }`, el canal de avisos de Google Drive de la planilla) |
| `POST /integrations/google/authorize` | Con token. `{ projectId? }` (de una de sus organizaciones). 200 `{ url }`: la URL de Google para pedir el permiso, con un `state` que sirve una vez, vence en 10 minutos y recuerda a la persona y el proyecto |
| `GET /integrations/google/callback` | La vuelta de Google, sin token: valida el `state`, canjea el código y guarda la cuenta de Google de la persona del `state`, con el refresh token cifrado. Redirige (302) a `/conectores?proyecto=…&google=conectado`, o a `/conectores?proyecto=…&google=error&motivo=…` |
| `DELETE /integrations/google` | Con token. 204. Borra la cuenta de Google de quien lo pide. Las planillas que vinculó siguen en sus proyectos, sin cuenta que las lea |
| `POST /integrations/google/notifications` | Los avisos de Google Drive, sin token: lo que vale es el secreto del canal (`X-Goog-Channel-Token`). 204, y revisa la planilla tras 2 s de calma si el aviso lo pide; 204 sin hacer nada si el canal no se conoce o si los avisos están apagados (sin `GOOGLE_WEBHOOK_URL` o sin Google configurado); 403 `invalid_channel_token` si el secreto no calza o si `X-Goog-Resource-ID` viene y no es el del canal; 400 `invalid_notice` si faltan `X-Goog-Channel-ID` o `X-Goog-Resource-State` |
| `POST /integrations/autodesk/webhooks` | Los webhooks de Autodesk (APS), sin token: lo que vale es la firma `x-adsk-signature: sha1hash=<HMAC-SHA1 del cuerpo crudo>` con `APS_WEBHOOK_SECRET`. 204 si el aviso es nuevo (lo guarda en `autodesk_events` y deja una línea en el log) y también si es un repetido (sin guardar ni avisar de nuevo); 403 `invalid_signature` si falta la firma o no calza; 400 de Nest (sin `code`) si dice ser `application/json` y no es JSON válido, antes de revisar la firma; 400 `invalid_webhook` si el cuerpo no es un webhook; 503 `autodesk_webhooks_off` sin `APS_WEBHOOK_SECRET` ([cambios en Autodesk](../../docs/spec/cambios-autodesk.md#el-receptor)) |
| `POST /integrations/projects/:projectId/sources` | Con token y el proyecto. 201 `{ source }`. `{ url }`: vincula la planilla al proyecto con la cuenta de Google de quien la vincula y guarda su primera revisión, sin avisar nada. Si la planilla ya estaba en el proyecto sin cuenta, la toma con la cuenta de quien la vincula. 422 `invalid_sheet_url`, 409 `not_connected` o `already_linked`, 502 `provider_error` si Google no la entrega |
| `POST /integrations/projects/:projectId/sources/:id/check` | Con token y el proyecto. 200 `{ source, check: { status, message, cells } }`: revisa la planilla ahora, en la misma fila que el sondeo. `status`: `changed` (con `cells`, las celdas que cambiaron, o `null` si la API no tenía la revisión anterior), `unchanged` o `failed`. 404 `source_not_found` si la planilla es de otro proyecto |
| `DELETE /integrations/projects/:projectId/sources/:id` | Con token y el proyecto. 204. Desvincula la planilla del proyecto y, con avisos, antes cierra su canal de Drive (`UnsubscribeSource`; si Drive falla, desvincula igual) |
| `GET /projects/:projectId/proposals?status=` | `{ proposals }`: el PR de cada revisión. Trae `documentId`, `label`, `revision`, `hunks` (los que cambian y, con `changed: false`, los que quedan como contexto), `unchangedHunks`, `checks` (`cost`, `schedule` y `overlaps` con sus conteos), `overlaps`, `blockedByOverlap` y `waitingFor` («Espera la validación del solapamiento»); el costo y el atraso son la suma de sus hunks. Cada revisor trae `stakeholderId`, `notificationId` y `decision` (`approve`, `dispute` o `null`). `status`: `open`, `disputed`, `merged`, `withdrawn`, `replaced` o `active` (abiertas y en disputa) |
| `POST /projects/:projectId/notifications/:id/response` | `{ kind: "reviewed" \| "issue", note? }`: el voto. Responde `{ notification, proposal, merged, stale, projectVersion }` |
| `POST /projects/:projectId/proposals/:id/reopen` | La autora reabre una propuesta en disputa: solo quien disputó vuelve a pendiente. Responde la propuesta |
| `POST /projects/:projectId/proposals/:id/withdraw` | La autora retira la propuesta. Responde la propuesta |
| `POST /projects/:projectId/discrepancies/:id/dismiss` | 204. El dueño del valor descarta la discrepancia; `{ note? }` opcional. Repetirlo no cambia nada ni emite otro evento |
| `POST /projects/:projectId/stale/acknowledge` | 204. `{ revisionId, note }`: el dueño del documento confirma sin cambio; la nota es obligatoria |
| `GET /projects/:projectId/changes?limit=20` | Los cambios más recientes (hasta 50), cada uno con su `impact`, sus `notifications` y su `proposal` |
| `GET /projects/:projectId/changes/:id` | Un cambio con su impacto, sus avisos y su propuesta; 404 si no existe |
| `GET /me` | Con `Authorization: Bearer <token de Auth0>`. `{ user: { id, email, name }, superadmin, organizations: { id, name, role }[] }`. La primera vez registra a la persona con el correo de su perfil, solo si ese correo tiene una invitación pendiente (403 `email_not_verified` si no lo confirmó). En cada entrada acepta las invitaciones pendientes a su correo, y quien queda sin organización no entra (403 `not_invited`, sin registrarlo). Un superadmin entra sin invitación y sin organizaciones. 401 `login_required` sin token, 401 `invalid_token` si no vale, 503 `auth_not_configured` sin `AUTH0_DOMAIN` y `AUTH0_AUDIENCE` |
| `GET /projects` | Con token. `{ projects: { id, organizationId, name, location, description }[] }`: solo los de sus organizaciones, del más antiguo al más nuevo |
| `POST /projects` | Con token y siendo parte de la organización (403 `not_a_member`). `{ organizationId, name, location?, description? }`: el nombre de 1 a 120 caracteres, el lugar hasta 200 y la descripción hasta 1000, recortados (400 si no cumple). Responde 201 `{ id, organizationId, name, location, description }`. 409 `project_name_taken` si la organización ya tiene un proyecto con ese nombre, sin contar mayúsculas, tildes ni espacios de más. El id sale del nombre (`Edificio Las Encinas` → `edificio-las-encinas`, con `-2`, `-3`… si otra organización ya lo usa) |
| `GET /projects/:projectId` | Con token. `{ id, organizationId, organizationName, name, location, description, createdAt }`. 404 `not_found` si no existe o es de una organización ajena |
| `POST /organizations` | Con token y siendo `admin` de alguna organización (403 `admin_required`). `{ name }`, de 1 a 120 caracteres. 201 `{ id, name, role: 'admin' }`: crea la organización con un id que sale del nombre (`constructora-sur`, o `constructora-sur-2` si ya está) y deja a quien la crea como su administrador. 409 `organization_name_taken` si ya es parte de una con ese nombre (sin distinguir mayúsculas, tildes ni espacios de más) |
| `DELETE /organizations/:id` | Con token y rol `admin` (403 `admin_required`). 204. Borra la organización con sus membresías, sus invitaciones y su conexión con Autodesk. 409 `organization_has_projects` si tiene proyectos y 409 `last_organization` si es la única organización de quien lo pide |
| `GET /organizations/:id/members` | Con token y siendo parte de la organización (403 `not_a_member`). `{ members: { userId, email, name, role }[], invitations: { id, email, role, createdAt }[] }` (las pendientes) |
| `POST /organizations/:id/invitations` | Con token y rol `admin` (403 `admin_required`). `{ email, role: 'admin' \| 'member' }`. Crea o actualiza la invitación; 409 `already_member` si ya es parte. Se acepta sola cuando esa persona entra |
| `GET /admin/users` | Con token de superadmin (403 `superadmin_required`). `{ users: { id, email, name, createdAt, organizations: { id, name, role }[] }[], invitations: { id, email, organizationId, organizationName, role, createdAt }[] }`: todos los usuarios de la plataforma y las invitaciones pendientes |
| `GET /admin/organizations` | Con token de superadmin. `{ organizations: { id, name, createdAt, members, projects }[] }`, con la cantidad de miembros y proyectos |
| `POST /admin/organizations` | Con token de superadmin. `{ name }`, de 1 a 120 caracteres. 201 `{ id, name, createdAt, members: 0, projects: 0 }`: crea la organización con un id que sale del nombre, como `POST /organizations`, pero el superadmin no queda como miembro. 409 `organization_name_taken` si ya existe una organización con ese nombre en la plataforma (sin distinguir mayúsculas, tildes ni espacios de más) |
| `POST /admin/invitations` | Con token de superadmin. `{ email, organizationId, role }`. Invita un correo a cualquier organización, sin ser parte de ella; 404 `organization_not_found`, 409 `already_member`. Responde la invitación con `organizationName` |
| `GET /organizations/:id/integrations/aps` | Con token y siendo parte (403 `not_a_member`). `{ configured, connection }`: `configured` es `false` sin `APS_CLIENT_ID`, `APS_CLIENT_SECRET`, `APS_CALLBACK_URL` o `APS_TOKEN_KEY`; `connection` es `null` sin conexión, o `{ status: 'active' \| 'reconnect_required', autodeskUser: { id, email, name }, scopes, connectedById, connectedAt, refreshedAt }`. Nunca trae tokens. `Cache-Control: no-store` |
| `POST /organizations/:id/integrations/aps/authorize` | 200 con token y rol `admin` (403 `admin_required`). `{ url }`: la página de consentimiento de Autodesk (`/authentication/v2/authorize`) con el `state` sellado. Deja la cookie `vigente_aps_oauth` (HttpOnly, SameSite=Lax, 10 minutos, en la ruta del callback). 503 `aps_oauth_not_configured` sin configurar |
| `DELETE /organizations/:id/integrations/aps` | 204 con token y rol `admin`. Revoca el refresh token en Autodesk (si falla, sigue) y borra la conexión |
| `GET /integrations/aps/callback?code&state&error` | A donde vuelve Autodesk. Sin token: lo que vale es el `state` y la cookie. Canjea el código, guarda la conexión y redirige (302) a `/cuenta?autodesk=conectada`, o a `/cuenta?autodesk=error&motivo=<invalid_state \| access_denied \| code_rejected \| aps_unavailable>`. Borra la cookie en ambos casos |

Cabeceras:

- `Authorization: Bearer <token de Auth0>` identifica tu cuenta en las rutas de cuenta y del proyecto. Sin token, 401 `login_required`; si no vale, 401 `invalid_token`.
- `x-action-id: <id>` hace idempotentes la ingesta y los votos: la misma acción devuelve la respuesta de la primera. Se guarda en memoria del proceso (hasta 500), por proyecto y por persona.

Tipos de evento (`kind`; cada uno trae `message` en español y `refs` con los ids que toca): `revision.received`, `proposal.opened`, `proposal.disputed`, `proposal.reopened`, `proposal.merged`, `proposal.withdrawn`, `proposal.replaced`, `review.approved`, `discrepancy.opened`, `discrepancy.backed`, `discrepancy.dismissed`, `overlap.detected`, `overlap.voted`, `overlap.cleared`, `overlap.confirmed`, `overlap.resolved`, `stale.detected`, `stale.acknowledged` y `consensus.sealed`. Las transiciones del orquestador los insertan en la tabla `project_events`, en su misma transacción.

Errores de negocio:

| Código | Cuándo |
| ------ | ------ |
| 400 | La entrada no cumple su schema de zod |
| 401 `login_required` / `invalid_token` | Falta el token de Auth0, o no vale |
| 403 `not_on_team` | Tu cuenta no está en el equipo del proyecto (en las escrituras) |
| 403 `not_your_document` / `not_your_notification` / `not_author` / `not_owner` / `not_validator` | No eres dueño del documento, del aviso, de la propuesta, del valor, ni validador del solapamiento |
| 404 `unknown_document` / `not_found` | El documento no está en el registro del proyecto, o no existe el recurso (también un proyecto ajeno) |
| 409 `already_ingested` | Ya está en el repositorio esa revisión (`documentId` y `label`) |
| 409 `invalid_state` | Una regla del dominio lo impide: votar distinto de lo ya votado, votar una propuesta o un solapamiento cerrado, reabrir una que no está en disputa |
| 422 `invalid_claims` | La revisión trae sujetos o atributos que el proyecto no tiene, o un espacio distinto al del documento (el cuerpo trae `issues`) |
| 503 `inference_unavailable` | No se pudo leer un fragmento de texto libre: falta `ANTHROPIC_API_KEY`, o el modelo no respondió |
| 404 `source_not_found` | La planilla ya no está vinculada a ese proyecto |
| 409 `not_connected` / `already_linked` | Falta conectar tu cuenta de Google, o esa planilla ya está vinculada al proyecto |
| 422 `invalid_sheet_url` | El link no es de una planilla de Google Sheets |
| 502 `provider_error` | Google no entregó la planilla o el permiso (el mensaje dice por qué) |
| 503 `not_configured` | Faltan `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` o `INTEGRATIONS_ENCRYPTION_KEY` |
| 400 `invalid_webhook` | La firma de Autodesk calza, pero el cuerpo no es un webhook (el mensaje dice por qué) |
| 403 `invalid_signature` | Al webhook de Autodesk le falta `x-adsk-signature` o no calza con el cuerpo crudo |
| 400 (sin `code`) | El cuerpo dice ser `application/json` y no es JSON válido; Nest lo rechaza antes de revisar la firma |
| 503 `autodesk_webhooks_off` | Llegó un webhook de Autodesk y falta `APS_WEBHOOK_SECRET` |

- Los ids de propuestas, avisos, discrepancias, revisiones y cambios son UUID.
- Cada acción de escritura corre en una transacción de Postgres bajo un advisory lock; el voto además bloquea la fila de la propuesta con `SELECT … FOR UPDATE`.

## Estructura

```
src/
├── main.ts                       arranque: CORS, apagado ordenado y puerto
├── app.setup.ts                  APP_OPTIONS (rawBody, para la firma de Autodesk), prefijo /api, validación con schemas y filtro de errores (también los usan los tests)
├── app.module.ts                 los módulos de la app
├── config/                       variables de entorno validadas con zod
├── common/
│   └── provide-use-case.ts       registra un caso de uso de un contexto como provider de Nest
└── modules/
    ├── database/                 el PrismaClient (token PRISMA_CLIENT), global, y UnitOfWork (transacción con lock)
    ├── project/                  ProjectCatalogs (global): carga un proyecto de la base por su id, lo valida (project-schema.ts) y arma el ProjectCatalog: elenco, modelo, grafo, espacios, documentos, sujetos, atributos, grilla y huellas
    ├── health/                   /api/health y /api/health/ready
    ├── lake/                     buildLake(db, project, extractor?): los adapters y casos de uso de context-lake de un proyecto, sobre una transacción o el cliente
    ├── impact/                   buildImpact(db, project) (el grafo y los impactos de un proyecto), el ClaimReader (Claude, o ninguno sin clave), el vocabulario del proyecto y ExtractClaims (ImpactModule)
    ├── notification/             buildNotification(db, project): los avisos de un proyecto
    ├── coordination/             orquesta la cadena y expone las rutas del proyecto; `revision-body.ts` valida la ingesta, `chunk-reader.ts` lee los fragmentos de texto libre, `events.ts` y `events.service.ts` escriben y leen los eventos del proyecto
    └── integrations/             los conectores de context-integrations: la vista y el OAuth de Google, las planillas vinculadas, el sondeo, los avisos de Drive y LoggingChangeListener, que deja cada cambio en el log; y el receptor de los webhooks de Autodesk (AutodeskWebhooksController, AutodeskWebhooksService, ReceiveAutodeskEvent y LoggingAutodeskListener)
        └── aps/                  la conexión de una organización con su cuenta de Autodesk (OAuth de tres patas): TokenCipher, el estado sellado, los puertos TokenVault y ApsOAuthClient con sus adapters, ApsConnectionService, el controller y el módulo
tests/                            replica src/: Vitest, sin base de datos; fixtures/los-aromos.ts es un proyecto completo de prueba
```

- **Por proyecto.** Cada ruta del proyecto carga su `ProjectCatalog` con `ProjectCatalogs.load(projectId)` y se lo pasa a `QueryService` y a `CoordinationService`, que arman los adapters y casos de uso de ese proyecto con `buildLake`, `buildImpact` y `buildNotification`. Cada adapter Prisma recibe `project.id` y filtra por él. La API arranca sin ningún proyecto en la base.
- **`CoordinationService`** es el único que conoce los contextos. Antes de la transacción, `ChunkReader` lee con `ExtractClaims` los fragmentos de texto libre (los estructurados pasan tal cual). Una ingesta hace, en una transacción: `IngestRevision`, y con el borrador de la revisión arma la base y el siguiente de todos los elementos que cambian con `elementsFromBaseline`, llama a `DetectChanges` (un cambio por elemento), a `AnalyzeChange` por cada uno y a `NotifyStakeholders` una vez (un aviso por afectado, con sus hallazgos de todos los hunks), y abre la propuesta con `OpenProposal` (revisores: la unión de los afectados; filtrados: los de `impact` que no son revisores). Después corre `ResolveOverlaps`, `OpenOverlaps` y `SettleOverlaps`, que fusiona lo que quedó listo. Un voto pasa por `RecordReview` (que no fusiona con solapamientos vivos), `RespondToNotification` y `SettleOverlaps`; al reabrir, `ReopenProposal` y `ReopenResponse` para quienes disputaron. El voto de un solapamiento pasa por `VoteOverlap` y `SettleOverlaps`.
- **`QueryService`** arma las vistas (lo vigente, procedencia, espacios, bandeja, propuestas y cambios) desde los repositorios del lago y los casos de uso de lectura de un proyecto.
- **Transacciones.** `UnitOfWork.run` abre una transacción interactiva, toma un `pg_advisory_xact_lock` (`LAKE_LOCK`) y entrega un cliente con el que `buildLake`, `buildImpact` y `buildNotification` crean sus adapters y casos de uso: todo lo que hace una acción queda en la misma transacción.
- **Totales.** El costo del proyecto es el presupuesto base del modelo más el `costDelta` de las propuestas fusionadas; el plazo es la entrega vigente más sus `delayDays`; la versión del proyecto es 1 más las propuestas fusionadas.
- **Eventos.** `CoordinationService.track` compara el estado antes y después de cada transición (propuestas, solapamientos, desfases, sello) y, con los eventos explícitos de la acción, los inserta en la misma transacción.
- **Variables.** `ANTHROPIC_API_KEY` (opcional; ausente o vacía, la API no lee texto libre). El conector de Google Sheets usa `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI`, `INTEGRATIONS_ENCRYPTION_KEY`, `INTEGRATIONS_POLL_SECONDS` y, para que Google avise al instante, `GOOGLE_WEBHOOK_URL`, `INTEGRATIONS_WATCH_HOURS` e `INTEGRATIONS_FALLBACK_SECONDS`. Las cuentas usan `AUTH0_DOMAIN` y `AUTH0_AUDIENCE`; la conexión con Autodesk, `APS_CLIENT_ID`, `APS_CLIENT_SECRET`, `APS_CALLBACK_URL` y `APS_TOKEN_KEY`; y los webhooks de Autodesk, `APS_WEBHOOK_SECRET`. Todas son opcionales: la API arranca sin ellas ([arquitectura](../../docs/arquitectura.md#web-y-api)).
- **Conectores.** `modules/integrations` arma los casos de uso de `context-integrations` solo si están el cliente de Google y la clave de cifrado; si no, la vista dice que falta configurar Google. `IntegrationsService` revisa las planillas vinculadas cada `INTEGRATIONS_POLL_SECONDS`, de a una y nunca dos veces la misma en paralelo, y anota en el log solo los errores nuevos. Con `GOOGLE_WEBHOOK_URL`, suscribe cada planilla a los avisos de Drive y los renueva antes de que venzan, con un timer propio (cada mitad del margen de renovación) que corre aunque `INTEGRATIONS_POLL_SECONDS` sea 0; la suscripción, la baja y las revisiones de una misma planilla van en la misma fila; `POST /api/integrations/google/notifications` (sin cuenta, validado con el secreto del canal) recibe los avisos y revisa la planilla tras 2 s de calma, y el sondeo queda de respaldo cada `INTEGRATIONS_FALLBACK_SECONDS`. Es un canal de conexión y escucha: `WatchSource` compara cada revisión con la anterior (que vive en memoria) y `LoggingChangeListener` deja en el log qué celdas cambiaron. No interpreta las planillas, no toca la cadena y no guarda lo que escucha. Cómo configurar Google: [integrations](../../context/integrations/README.md).
- **Webhooks de Autodesk.** `POST /api/integrations/autodesk/webhooks` lee el cuerpo crudo (la app se crea con `rawBody` de Nest, en `APP_OPTIONS`) y `AutodeskWebhooksService` lo verifica con `verifyApsWebhook` y `APS_WEBHOOK_SECRET` antes de mirarlo (el parser JSON de Nest corre antes: un JSON roto recibe 400 sin llegar a la firma). Si pasa, `ReceiveAutodeskEvent` guarda la llave del aviso en `autodesk_events` (`PrismaAutodeskEventRepository`) y, si es nueva, `LoggingAutodeskListener` deja en el log `Conectores` una línea como `Autodesk: version.added «Muro.rvt» (v3) por <usuario> en <proyecto> / <carpeta>; el diff por elemento queda pendiente`. Sin el secreto, la ruta responde 503 y el log lo dice una vez. El diff por elemento con AEC Data Model y registrar los webhooks en Autodesk todavía no están ([cambios en Autodesk](../../docs/spec/cambios-autodesk.md#lo-que-falta)).
- **Lectura de texto libre.** Con `ANTHROPIC_API_KEY`, el `ClaimReader` es `CachedClaimReader(ClaudeClaimReader)` con una caché en memoria: la misma consulta no vuelve a salir a la red mientras viva el proceso. Sin clave es `UnavailableClaimReader`, que falla con `InferenceUnavailableError`: la ingesta de un fragmento de texto libre responde 503 `inference_unavailable` y los fragmentos estructurados entran igual. Sin clave no sale nada a la red.
- **El proyecto.** `ProjectCatalogs.load(projectId)` lee de la base la definición del proyecto en cada pedido, la valida con `project-schema.ts` y entrega un `ProjectCatalog`. Si no existe, 404 `not_found`; si está mal formada, falla y dice por qué. Un proyecto recién creado (sin espacios, documentos, sujetos, modelo ni grilla) también carga: las vistas salen vacías y no hay documentos a los que subirles revisiones. Las vistas reciben el catálogo dentro del `LakeSnapshot`.
- **Modelo de áreas.** Sale de la definición del proyecto: los niveles, los ejes longitudinales con sus metros, los transversales, los sistemas y la huella de cada sujeto. Una huella es una regla en datos: el tipo (`soporte` u `ocupante`), los niveles, las celdas (`all`, las de un eje transversal, o la del tramo donde cae un atributo de posición sobre un eje) y los sistemas. En el proyecto de prueba de los tests (`tests/fixtures/los-aromos.ts`), las losas son soporte; el shaft S1, las ventanas y el colector B2 son ocupantes; y las partidas y el proyecto no ocupan espacio. El lago recibe el modelo como `project.footprintModel`.

## Cuentas, organizaciones y roles

Todas las rutas del producto (`/me`, `/projects` y lo que cuelga de cada proyecto, `/organizations/*`, `/admin/*` y las de conectores) piden una cuenta. Solo `/health`, `/aps/*` y las vueltas de OAuth (`/integrations/google/callback`, `/integrations/aps/callback`) no la piden.

- **Auth0 solo dice quién es.** `AccountGuard` lee el `Bearer`, y `Auth0Identity` lo valida con `jose` contra las llaves públicas del tenant (`https://<AUTH0_DOMAIN>/.well-known/jwks.json`), el emisor y la audiencia `AUTH0_AUDIENCE`, en RS256. La primera vez que llega un `sub`, pide el perfil a `/userinfo` para tener el correo confirmado.
- **Lo demás vive en Postgres.** `users` (por `auth_subject` y correo), `organizations`, `memberships` con su rol e `invitations` por correo. Cada proyecto es de una organización.
- **Proyectos.** Cualquier miembro de una organización crea un proyecto en ella (`POST /projects`), con un nombre que no repita el de otro proyecto de la organización. Queda con lo básico: nombre, lugar, descripción y quien lo creó como único integrante del elenco (rol «Creador del proyecto», canal `email`) y como autor y dueño del costo y del plazo. Sin espacios, documentos, sujetos, modelo, partidas, tareas, dependencias ni grilla, así que la cadena no tiene todavía a qué subirle revisiones.
- **Roles.** `admin` configura la organización, invita, la elimina y crea otras; `member` es parte del equipo, ve sus proyectos y crea otros. Autor y afectado no son roles: cambian de un cambio a otro ([negocio](../../docs/negocio.md#actores)).
- **Superadmin.** Es un permiso de la plataforma, no un rol de una organización: es superadmin quien entra con un correo de `SUPERADMIN_EMAILS` (separados por coma, sin importar mayúsculas). Nadie lo da ni lo quita desde la web. Entra sin invitación, ve a todos los usuarios, crea organizaciones sin quedar en ellas e invita a cualquiera (`AdminController`, `AdminService`); `requireSuperadmin` responde 403 `superadmin_required` al resto.
- **Solo se entra por invitación.** Un administrador de la organización o un superadmin invita un correo; la cuenta no existe hasta su primer login, y mientras tanto la invitación es el usuario pendiente. Quien entra con ese correo confirmado queda como miembro con el rol de la invitación. Quien entra sin invitación, o se queda sin organizaciones, recibe 403 `not_invited` en cada ruta de cuenta, y si es su primera vez no queda registrado: no hay cuentas sin organización, salvo las de los superadmins. En local, `pnpm db:seed` deja la organización Constructora Cordillera con un administrador y cinco miembros invitados ([semilla](../../data/main/README.md#la-semilla)).
- **Organizaciones.** Un administrador de cualquier organización crea otra (`POST /organizations`) y queda como su administrador; la semilla crea la primera, Constructora Cordillera, si la base no tiene ninguna. Eliminar (`DELETE /organizations/:id`) no toca proyectos: una organización con proyectos no se elimina, y la base lo respalda (`Project → Organization` es `onDelete: Restrict`). Tampoco se elimina la única organización de quien lo pide, porque sin organizaciones no podría entrar.
- **Sin Auth0 configurado** la API arranca igual y esas rutas responden 503 `auth_not_configured`.

## Conexión con Autodesk

Para leer los proyectos de Autodesk Construction Cloud, un administrador de la organización conecta una vez su cuenta de Autodesk. La conexión es de la organización (una por organización, tabla `aps_connections`) y guarda quién la hizo. Es un módulo de la API, `modules/integrations/aps`, no un contexto: sus puertos y adapters viven ahí.

- **Configuración.** Usa una app de APS (`APS_CLIENT_ID`, `APS_CLIENT_SECRET`), más `APS_CALLBACK_URL` y `APS_TOKEN_KEY`. Si falta alguna, la API arranca igual: el estado responde `configured: false` y conectar, 503 `aps_oauth_not_configured`.
- **El flujo.** `POST …/authorize` arma la URL de `/authentication/v2/authorize` (`response_type=code`, scopes `data:read account:read user-profile:read`) con un `state` que es `{ organizationId, userId, nonce, expiresAt }` cifrado con `APS_TOKEN_KEY` (10 minutos), y deja el `nonce` en una cookie HttpOnly. El callback abre el `state`, lo compara con la cookie en tiempo constante (así un enlace de callback ajeno no conecta nada: CSRF), canjea el código en `/authentication/v2/token` como cliente privado, pide el perfil (`/userinfo`) y guarda la conexión. El callback y la cookie pasan por la web, así que `APS_CALLBACK_URL` apunta a `<web>/api/integrations/aps/callback`, y al terminar se redirige a `/cuenta` del mismo origen. Que la persona sea administradora se revisa al pedir la URL.
- **Refresh token.** APS v2 entrega un refresh token con el código, sin un scope extra, que vale 15 días y se rota en cada renovación: el nuevo reemplaza al anterior (si APS no manda otro, se queda el que había).
- **Cifrado.** `TokenCipher` usa AES-256-GCM de `node:crypto` con un IV aleatorio de 12 bytes y el tag de 16; el texto queda como `v1.<iv>.<tag>.<cifrado>` en base64url. El access y el refresh token van en columnas separadas, cada uno con su contexto (`aps:<organización>:access_token`) como datos asociados, así que un texto copiado a otra fila o a otra columna no se descifra. Si `APS_TOKEN_KEY` cambia, las conexiones guardadas quedan en `reconnect_required`.
- **Renovación sola.** `ApsConnectionService.getValidAccessToken(organizationId)` es lo que usan las lecturas a Autodesk: entrega el access token guardado si le quedan más de 5 minutos, y si no, lo renueva con el refresh token y guarda los dos tokens nuevos. Dos pedidos a la par renuevan una sola vez (la API corre en un proceso). Si Autodesk rechaza la renovación (400, 401 o 403), la conexión queda en `reconnect_required` y no se reintenta hasta reconectar; si APS no responde, sigue activa. Además, cada 6 horas renueva las conexiones activas que llevan una semana sin renovarse, para que el refresh token no venza sin uso.
- **Errores** de `ApsConnectionError`: `not_connected`, `reconnect_required`, `aps_unavailable`, y en el callback `invalid_state`, `access_denied` y `code_rejected`.
